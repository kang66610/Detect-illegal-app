# Appium 遍历器深度模块化设计

## 背景

当前遍历器已经拆出同意、权限、登录、隐私中心、文档、恢复与动作裁决等若干文件，但 `agent/detection_engines/appium_explorer.py` 仍承担大量运行状态读写、页面语义判断、动作二次覆盖、场景完成标记和 LLM 上下文拼装。拆出的部分模块仍直接读写同一个字符串键字典，因此文件数量增加了，但关键不变量尚未集中。

本次重构覆盖八项能力：统一运行状态、唯一动作裁决、统一页面语义、规则场景执行、LLM 提案、全部人工基准、时间线回放以及性能预算。目标不是继续按 App 名称添加特判，而是形成可复用、可回放、可验证的通用遍历架构。

## 目标与非目标

### 目标

1. 任何跨步骤状态只能通过统一运行状态模块改变。
2. 每轮页面最多产生一个最终动作，所有候选动作经过同一裁决链。
3. 页面角色与目标语义只由统一语义模块输出，业务决策模块不重复解析原始 UI。
4. 动态规则只能由场景执行器凭对应证据进入完成状态。
5. LLM 只提出受约束的候选动作，不能直接改变运行状态或宣告覆盖完成。
6. 仓库中每份可解析人工报告都能形成独立回归基准，且不会向检测结果注入答案。
7. 真实检测时间线可以脱敏回放，用于跨 App 回归。
8. 等待、重试、OCR、LLM 与恢复均受统一预算约束并能输出耗时指标。

### 非目标

- 不引入 App 名称、包名或页面标题特判来指导遍历。
- 不把人工报告中的违规结论作为自动检测证据。
- 不改变现有规则编号含义。
- 不在没有设备侧、文档、网络或人工补充证据时把“未执行”报告为“未发现违规”。
- 不在本次重构中替换 Appium、OCR、Frida 或模型供应商。

## 总体架构

每轮遍历采用单向流水线：

`观察页面 → 生成语义快照 → 更新运行状态 → 场景生成候选动作 → LLM 生成候选动作 → 统一裁决 → 执行动作 → 验证效果 → 记录证据与检查点`

主循环只负责调度上述步骤和处理取消/暂停，不再包含页面角色判断、规则完成逻辑或动作覆盖条件。旧函数在迁移期可以作为兼容代理，但代理不得拥有第二份状态或决策规则；迁移完成后删除。

## 1. 统一运行状态

### 设计

扩展 `DetectionRunState`，把状态分为以下领域子状态：

- 阶段状态：observe、deny、allow 及阶段继承策略。
- 导航状态：语义路径、待探索边、已验证边、恢复检查点。
- 文档状态：文档身份、正文类型、滚动进度、完成/中断/失败原因。
- 权限状态：触发入口、弹窗、拒绝/允许结果、业务重试结果。
- 登录状态：页面候选、等待、验证、超时、测试账号执行结果。
- 场景状态：规则场景步骤、尝试次数、证据和终止原因。
- 预算状态：页面、动作、时间、重试和外部调用消耗。

所有改变不变量的操作通过状态对象的方法完成。底层仍可序列化为 JSON，但检查点必须带 `schema_version`，恢复时验证版本并执行明确迁移。未知字段保留，非法枚举和矛盾状态转为可见恢复缺口，不能静默纠正成成功。

### 阶段规则

- deny 阶段从清空应用数据和权限后的初始状态开始。
- allow 阶段再次清空运行时权限，但复用第一阶段已验证的非权限导航图和文档阅读事实。
- allow 阶段只重放与“同意后收集、允许权限后的行为差异”有关的安全路径，不重复无关文档和普通业务页面。
- 登录超时永远不能设置登录已验证；权限请求动作与设备实际授权结果必须分开保存。

## 2. 唯一动作裁决

### 候选来源

- 安全与系统页面退出。
- 活跃规则场景。
- 文档阅读会话。
- 权限、同意、登录、隐私中心等领域决策。
- DFS 导航前沿。
- LLM 受约束提案。
- 恢复与无效果动作处理。

### 裁决顺序

先进行不可覆盖的安全过滤，再按活跃场景、恢复任务、文档完整性、DFS 前沿和 LLM 建议排序。低价值页面只能观察一次并退出；已验证无效果或达到重试上限的目标进入阻断集合。裁决器返回最终动作、来源、被覆盖候选及理由。主循环不得在裁决后再次改写动作。

一个页面周期只允许执行一个最终动作。动作效果验证在下一次稳定观察后完成，并把结果反馈给导航、场景和预算状态。

## 3. 统一页面语义

### 输入

- Activity、包名及窗口类型。
- Appium 元素树及可交互属性。
- OCR 文本和可选截图视觉特征。
- 来源语义路径、前一个动作和当前阶段。
- 已确认文档身份、系统页面允许清单和稳定页面指纹。

### 输出

输出不可变的页面语义快照，至少包括：页面角色、稳定语义指纹、所属包范围、文档类型、是否允许深搜、推荐退出方式、候选目标及每个目标的语义标签。

页面角色优先级固定为：系统/外部页面、权限弹窗、文档正文、业务交互页、隐私治理入口页、登录页、低价值页。已确认的文档正文不能因“暂无内容”“购买”等局部文字被剪枝。登录页必须同时满足输入控件结构或明确认证语义，注销、更换手机号等单一文字不能触发 120 秒登录等待。

通用入口使用语义簇而非固定名称，包括账号与个人资料、设置、隐私治理、投诉/反馈/帮助/联系渠道、头像或媒体选择、注销/删除账号、权限相关业务入口。

## 4. 规则场景执行器

每项需要动态操作的规则由场景模板描述：前置条件、目标语义、动作序列、期望观察、允许恢复方式、成功证据、无违规证据和阻塞原因。

以 4.2 为例，必须经历：选择与权限相关的业务入口、观察权限弹窗、执行拒绝、恢复或返回业务页、重试同一语义业务动作、比较拒绝后的功能结果。只有观察到阻断或功能可继续的结果证据后才能终止。单纯看到权限弹窗、页面文字或执行一次返回不算完成。

场景执行器拥有场景状态转换，其他模块只能提交观察事件。导航耗尽与规则覆盖完成分离：DFS 无安全目标时仍可能存在“requires_login”“blocked_external”“not_executed”等场景结果，报告必须如实展示。

## 5. LLM 提案适配器

LLM 适配器接收页面语义快照、未完成场景摘要、DFS 候选和已阻断目标，生成结构化候选动作。传给模型的目标必须来自当前可见目标白名单；模型不能生成任意坐标、规则结论、状态更新或直接结束未完成场景。

提示词具有显式版本号。每次调用保存脱敏后的输入摘要、候选动作、解析结果、降级原因、耗时和最终是否被裁决器采用。模型不可用、格式错误或建议越界时退回确定性 DFS/场景策略，不中断遍历。

离线评估使用保存的语义快照，不调用真实设备；指标包括合法动作率、场景推进率、重复点击率、低价值点击率及裁决覆盖率。

## 6. 全量人工报告基准

新增报告基准导入流程，从 `app人工检测报告` 解析 App 名称、包名映射、规则编号、人工描述和必要前置场景。解析结果保存为结构化基准数据并支持人工校对。

基准分为两层：

- 规则召回基准：比较自动报告与人工报告的规则集合。
- 时间线基准：比较关键场景里程碑的有序事件，不要求依赖具体控件文字。

人工基准仅用于回归评价，绝不能改变遍历优先级、制造违规证据或注入自动报告。未建立包名映射、规则编号无法解析或报告版本不明时输出显式基准缺口。

## 7. 脱敏时间线回放

定义可版本化回放格式，记录页面语义输入所需的 Activity、包范围、元素属性、OCR 摘要、动作、动作效果、权限状态和证据事件。账号、输入内容、设备标识、完整截图路径及个人信息在落盘前脱敏。

回放执行同一状态、语义、场景和裁决模块，但使用记录适配器代替真实 Appium、OCR 和 LLM。回放必须支持：

- 按完整检测重放。
- 从任意检查点恢复。
- deny 与 allow 两阶段对比。
- 固定某一 LLM 提案以验证确定性裁决。
- 对所有人工报告基准运行回归。

真实设备新增问题必须先保存为最小回放夹具，再修复对应模块。

## 8. 性能预算与完成条件

每轮检测记录：页面观察耗时、稳定等待耗时、OCR 耗时、LLM 耗时、Appium 动作耗时、恢复耗时、页面访问数、重复/无效果动作数和各场景推进量。

预算按照页面角色和场景价值分配，而不是全局固定点击次数：

- 文档正文持续滚动到经过重复确认的底部，不使用固定 20 次上限；卡住重试仍受独立时间和无位移预算约束。
- 权限及活跃规则场景可获得恢复预算。
- 广告、购买、会员、邀请奖励、刷新付费等低价值页只观察一次。
- 同一稳定页面与同一语义目标连续无效果后阻断，并返回 DFS 上一级。

完成条件同时要求：安全 DFS 前沿耗尽、无待验证动作、所有可执行场景达到有证据的终态、检查点已持久化。达到总时间上限但场景未完成时，以覆盖缺口结束，不能伪装为完整检测。

## 兼容与迁移策略

采用逐模块替换，不进行一次性重写：

1. 先建立状态和事件兼容层，旧报告读取路径保持可用。
2. 将现有分支改为产生候选动作，不直接执行或写最终决策。
3. 迁移页面语义函数并通过删除测试确认主循环不再拥有重复规则。
4. 把现有场景完成调用替换为观察事件。
5. 将 LLM 上下文拼装迁入适配器。
6. 接入人工基准、回放和预算门禁。
7. 删除兼容代理及不再使用的字符串状态键。

所有迁移步骤必须保持已有报告字段兼容；新增字段只能追加。恢复检查点不兼容时必须安全重启当前阶段并保留已落盘证据，不能加载为成功状态。

## 错误处理与可观测性

- Appium 会话失效：保存检查点，恢复会话，重放最近的安全语义路径。
- 应用自定义崩溃页或相机页：优先返回；返回无效果才升级到重启应用。
- 应用加载卡住：在稳定指纹无变化达到预算后关闭后台并重启，再重放路径。
- LLM/OCR 不可用：记录能力缺口并使用确定性策略。
- 文档来源或标题不一致：以正文语义和来源路径联合确定身份，并记录不一致证据。
- 冲突证据：保留双方并输出待复核，不静默删除。

## 测试策略

每项修改遵循测试先行：

1. 状态转换与检查点版本单元测试。
2. 候选动作裁决优先级、不可覆盖安全规则和来源真实性测试。
3. 页面语义表驱动测试，覆盖已有 App 暴露的页面形态但不使用 App 名称作为输入。
4. 4.2、3.8、文档阅读、登录门禁和权限两阶段场景测试。
5. LLM 白名单、结构化输出、降级和提示词回放测试。
6. 所有人工报告结构化基准的解析与召回计算测试。
7. 案例C、案例K、案例G、案例H及其余报告应用的脱敏时间线回放测试。
8. 性能预算与停止条件测试。

最终验证分层运行：模块单元测试、Appium 遍历器测试、规则与报告测试、全部后端测试，再选取至少一个 deny/allow 真实设备冒烟检测。真实设备不可用时必须明确说明未执行，不能仅凭单元测试宣称端到端完成。

## 验收标准

- 主循环不再直接写领域运行状态，不再在最终裁决后改写动作。
- 页面语义、动作裁决、规则场景和 LLM 提案各有唯一实现位置。
- 所有场景完成记录都带合法证据来源；错误事件名不能表达相反状态。
- 文档重复阅读、无效果重复点击和低价值页面深入点击受到统一抑制。
- deny 阶段先运行；allow 阶段只重放与同意/授权差异相关路径。
- 仓库内全部可解析人工报告均有规则召回基准；关键动态规则有时间线基准。
- 新 App 问题可以通过回放夹具复现，不需要在生产代码中添加 App 名称特判。
- 测试输出包含召回率、时间线通过率、无效动作率和各阶段耗时。
- 全部自动测试通过；真实设备冒烟结果与未覆盖能力分别报告。
